=== AI Best Practise

==== Tokens & "Thinking"

==== What "Thinking" Means

* Next-Token Predictors: Predict the most likely following text via statistical pattern completion.

* No Intrinsic Intent: No memory, beliefs or genuine understanding

* "Thinking" Models: Utilize chain-of-thought scratchpads (e.g. o1, Claude thinking) where '*more tokens = more reasoning

* Pattern Recognition: Matches against billions of learned patterns rather than understanding code semantics. -> Konsequenz: Es wird in markdown "programmiert", da auch die Quellen mit denen verglichen wird, natürlichsprachig sind.


==== Tokens Explained

* Token Units: LLM read tokens (~3/4 word), not raw characters

** Example: `kubectl apply -f deployment.yaml` -> 7 tokens

* Token Limits: Hard combined limit across input prompt and output completion.

* Trade-offs: More tokens increase cost and latency, but provide richer context.

=== Context & Window Management

* Complete Scope: System prompt + conversation history + user input + output response

** GPT-4o: 1M+ tokens (~2500 pages)
** Gemini: 1M+ tokens (~2500 pages)
** Claude: 1M+ tokens (~2500 pages)

* "Lost in the Middle" Effect: Bigger ungleich better; attention and reasoning degrade as context fills.

=== Context Management Rules

* Curate Relevance: Never dump entire repositories; provide only relevant snippets.

* Structured Formatting: Clear headings, markdown and bullet points assist parsing.

* Primacy & Recency: Place critical constraints at the beginning and end.

* Reset Often: Start fresh conversation when switching topics to avoid stale context.



=== Prompt Engineering

==== Prompt Engineering: Basics

* Vague Prompt: `"Write me a Dockerfile"` -> unpredictable output.

* Specific prompt: `"Write a multi-stage Dockerfile for Go 1.24, non-root nuser, pinned digests, no hardcoded secrets"`

* Core Rule: The more contraints you specify, the better the output.


==== Prompt Engineering: Advanced

* System Prompts: Explicitly define persona and role (e.g. `"You are a K8s security auditor"`). -> ganz schlecht. Er ist kein Experte und würde nichts mahr nachsehen.

* Few-Shot examples: Provide 1-2 examples of target input/output pairs.

* Chain-ofThought: Use `"Think step by step"` to enforce reasoning before answers.

* Iterative Refinement: Avoid one-shot expectations; generate, critique and improve.


=== Spec-Driven Development (SDD)

Architecting software with AI as the builder.

==== Spec-Driven Principles (SDD) - Architecting Software with AI as the Builder

* Role Separation: You are the architect, *AI is the builder*.

* Explicit Requirements: Define constraints, behaviors and edge cases up front.

* Acceptance Criteria: Specify measurable tests and verification steps.

* Objective Review: Review AI outputs strictly against the spec, not gut feeling.

==== The SDD Workflow

[cols="1,1,1,1", options="header"]
|===
|01 Spec |02 Generate |03 Review |04 Iterate

|Define what to build
|AI writes the code
|Check against spec
|Refine with feedback
|===

NOTE: The spec is your source of truth -- not the AI, not your assumptions.

=== Key Takeaways

[quote]
"AI doesn't think. It predicts. Your job is to think for it."

* Manage Context: Keep inputs minimal, structured and focused.

* Write Specs: Direct implementation with strict constraints and criteria.

* Prompt Precisely: Use roles, few-shot examples and chain-of-thought.

* Review Everything: Verify thoroughly against the specification.

Ein Vorgehensmodell sagt, in welcher Reihenfolge man in einem Projekt arbeitet.
Es legt fest, wann geplant, wann gebaut und wann geprüft wird.

.Tafelbild: die vier Modelle nebeneinander
image::tafelbild/vorgehensmodelle.png[Vorgehensmodelle am Tafelbild, 900]

=== Wasserfall

Eine Phase nach der anderen. Eine Phase ist fertig, bevor die nächste startet.

[cols="1,3", options="header"]
|===
|Phase |Was passiert

|IST |Ist-Zustand aufnehmen: Was gibt es schon?
|GE |Grobentwurf: die grobe Struktur des Systems
|FE |Feinentwurf: die Details festlegen
|IMPL |Implementierung: Code schreiben
|BW |Betrieb und Wartung
|===

* Vorteil: einfach zu verstehen und leicht zu planen.
* Nachteil: Änderungen am Ende sind teuer, weil man zurück in frühere Phasen muss.
* Fehler im Entwurf fallen erst spät auf.
* Passt nur, wenn die Anforderungen von Anfang an feststehen.

=== RUP (Rational Unified Process)

Am Tafelbild sind die Kästen versetzt und überlappen sich. Genau das ist der Punkt:
die Phasen laufen nicht streng nacheinander.

* Vier Phasen: Inception, Elaboration, Construction, Transition.
* Die Phasen überlappen sich und werden mehrmals durchlaufen (iterativ).
* Risiken werden früh angegangen, nicht erst am Schluss.
* Die Architektur steht im Mittelpunkt.

=== Scrum (agil)

* Die Arbeit läuft in kurzen *Sprints*, zum Beispiel zwei Wochen.
* Im *Product Backlog* stehen alle Wünsche, nach Wichtigkeit sortiert.
* Jeder Sprint liefert ein *Inkrement*: etwas, das man benutzen kann.
* Nach jedem Sprint gibt es Review und Feedback, danach wird neu priorisiert.

NOTE: Scrum garantiert kein gutes Produkt. Es sorgt nur dafür, dass man früh und oft merkt, wenn etwas falsch läuft.

=== Spec-Driven Development (SDD)

. *Spec schreiben:* Was soll rauskommen? Welche Grenzen gibt es? Woran messe ich das Ergebnis?
. *Bauen lassen:* Die KI schreibt den Code.
. *Prüfen:* Ergebnis gegen die Spec halten, nicht gegen das Bauchgefühl.
. *Nachbessern:* Abweichungen korrigieren und wieder prüfen.

Du bist der Architekt, die KI ist der Bauarbeiter.

IMPORTANT: Die Spec ist die Quelle der Wahrheit -- nicht die KI und nicht die eigene Erinnerung.

=== Die vier Modelle im Vergleich

[cols="1,2,2", options="header"]
|===
|Modell |Ablauf |Änderungen unterwegs

|Wasserfall |streng nacheinander |teuer
|RUP |Phasen überlappen, mehrere Durchläufe |eingeplant
|Scrum |kurze Sprints |nach jedem Sprint möglich
|SDD |Spec -> bauen -> prüfen |Spec ändern, neu bauen lassen
|===

=== Tokens und "Thinking"



Eine KI *denkt nicht*. Sie sagt voraus, welches Token als Nächstes am besten passt.

* *Next Token Predictor:* Sie rät das wahrscheinlichste Muster, Token für Token.
* *Kein eigener Wille:* Kein Gedächtnis, keine Absicht, kein echtes Verstehen.
* *Pattern Recognition:* Sie vergleicht mit Milliarden gelernter Muster.
* *"Thinking"-Modelle:* Sie schreiben sich Zwischenschritte auf und finden sich dadurch in der Landschaft besser zurecht.

.Die KI sucht den tiefsten Punkt in der Landschaft. Dort liegt die perfekte Antwort.
image::tafelbild/3d-landschaft.png[Landschaft mit der perfekten Antwort, 700]

Die Kurve ist ein Bild für die Suche nach der Antwort. Die roten Punkte sind Stellen, an
denen die KI hängen bleibt: lokal sieht es gut aus, aber es ist nicht der tiefste Punkt.
Ein "Thinking"-Modell sucht weiter und landet eher unten.

=== Context Window



Die KI ist *zustandslos*. Sie erinnert sich an nichts. Bei jeder Anfrage wird der komplette
Context noch einmal mitgeschickt.

* Ein Token ist ungefähr ein Dreiviertel-Wort.
* Beispiel: `kubectl apply -f deployment.yaml` sind 7 Tokens.
* Das Context Window ist das Limit für alles zusammen: Anweisungen + Verlauf + Eingabe + Antwort.
* Aktuelle Agenten schaffen etwa 1M Tokens.
* Die KI beachtet *Anfang und Ende* am stärksten. Die Mitte geht unter.

.Context Management Rules
* Wichtiges an den Anfang und ans Ende schreiben.
* Nicht das ganze Repo reinkippen, sondern nur die relevanten Stellen.
* Bei einem neuen Thema einen neuen Chat starten.
* Billige Modelle (Haiku) für die Fleißarbeit: Brownfield-Code lesen, Websuche.
* Für lange Aufgaben einen Skill für den Continuation Prompt nutzen.

Zum Memory:

* Memory ist projektbezogen und liegt in einem eigenen Verzeichnis.
* Memory muss *klein* bleiben. Wird es zu groß, liest der Agent nicht mehr alles und vergisst Dinge.
* Bei *Worktrees* liegt das Arbeitsverzeichnis woanders -- das Memory ist dann weg.
* Auch die Commit-History ist Wissen. Dafür darf man aber nicht von Hand committen.

=== Skills, Commands, Rules, Tools und MCP



[cols="1,3", options="header"]
|===
|Baustein |Wofür

|Skill |Anleitung, die geladen wird, sobald passende Reizwörter im Prompt vorkommen.
|Command |Ein fester Ablauf, den man selbst startet -- für wiederkehrende Arbeiten.
|Rule |Vorgabe, die immer gilt.

* Im *Frontmatter* eines Skills stehen die Reizwörter. Passt eines davon, wird der Skill gelesen.
* Es gibt gemeinsame Skills und projektspezifische Skills.
* *Tools sparen Tokens.* Beispiel: Statt den ganzen Build-Output in den Context zu kippen, holt ein Tool nur die Fehlerzeilen heraus.

=== TDD und Submodules



Test-Driven Development in drei Schritten:

. *Rot:* Test schreiben. Er muss fehlschlagen -- der Code fehlt ja noch.
. *Grün:* Das Minimalste schreiben, damit der Test durchläuft. Nicht mehr.
. *Refactor:* Code aufräumen, die Tests bleiben grün.

Zwei Regeln:

* Beim Test schreiben wird *kein* Produktivcode geändert.
* Beim Produktivcode schreiben wird *kein* Test geändert.

NOTE: Skills, Commands und Rules liegen in einem eigenen Überrepo und werden als *Git-Submodule* in die Projekte eingebunden. So kann man sie in mehreren Repos verwenden.
